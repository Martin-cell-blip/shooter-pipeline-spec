# 管线总图（控制表）v0

> 对一条射击游戏生产管线的**外部拆解**：依据公开资料（官方补丁说明、公开 API、开发者公开分享）与长期玩家侧观察整理，不代表任何工作室的内部流程。
> 用途：先把六条子管线的**产出物、权威来源、依赖关系、可机检范围**列清楚，再决定 Agent 能接哪一段、校验器能证明什么。
> 本仓库**只实现其中一条竖切**（§3 数值 + §5 配置表，场景＝一次平衡性补丁），其余四条停在本表这一层。

## 0. 读表约定

每条子管线回答同样七个问题：

| 栏 | 含义 |
|---|---|
| 产出物 | 这条管线交付什么文件或数据 |
| 权威来源 | 出现分歧时以谁为准（一个事实只认一个来源） |
| 上游 / 下游 | 它读谁、谁读它 |
| 机器可证（FAIL 级） | 可枚举、可写成确定性检查的硬规则；违反即判 FAIL |
| 只能提示（REVIEW 级） | 启发式能找到候选，但对错要人判断；**命中不判 FAIL** |
| 留给人签字 | 机器给不了的判断，进人工签字清单 |
| Agent 可接的任务 | 在上述边界内，Agent 能执行且结果可被校验的工作 |

状态口径沿用四态：`PASS`（机器证明合规）／`FAIL`（机器证明违规）／`REVIEW`（只有候选）／`NOT_RUN`（缺输入未跑完，绝不因异常返回成功）。

## 1. 战斗（Combat）

| 栏 | 内容 |
|---|---|
| 产出物 | 武器与技能的行为定义：开火模式、命中判定类型（即时命中／弹道）、技能状态机、冷却与资源逻辑 |
| 权威来源 | 行为逻辑以战斗设计文档与运行时实现为准；**其中的数字不在这里**，统一引用 §3 |
| 上游 / 下游 | 读 §3 数值、§5 配置表；被 §2 关卡（交战距离）、§4 叙事（技能描述）引用 |
| 机器可证 | 每个技能引用的数值键在配置表中存在；状态机无不可达状态、无无出口状态；冷却与持续时间非负 |
| 只能提示 | 两个技能组合后是否出现无反制窗口；新机制与既有机制是否功能重复 |
| 留给人签字 | 手感、打击反馈、操作上限与下限是否合适 |
| Agent 可接 | 从行为定义生成"数值键引用清单"；检查引用完整性；为新技能起草状态机草稿供策划改 |

## 2. 关卡（Level）

| 栏 | 内容 |
|---|---|
| 产出物 | 地图几何与标注：视线长度、掩体、高低差、目标点与重生点、补给位置 |
| 权威来源 | 几何以关卡文件为准；交战距离类**度量值**以从关卡文件导出的度量表为准 |
| 上游 / 下游 | 读 §1 §3（武器有效距离）；被 §6 资源管线（场景资产）引用 |
| 机器可证 | 重生点到目标点路径可达；导出度量表字段齐全；补给点数量在约定区间 |
| 只能提示 | 某条主视线长度落在某武器"伤害衰减起点"以外／以内，导致该武器在此图显著占优或失效 |
| 留给人签字 | 节奏、攻防平衡感、是否好玩 |
| Agent 可接 | 平衡补丁改动衰减距离后，重算"各图主视线 × 各武器有效距离"交叉表并报出状态翻转的格子 |

> 跨管线约束示例：补丁把某武器"最小衰减距离"从 30 米改到 20 米，这不只是 §3 的一个数——它会改变 §2 里哪些视线对该武器有效。校验器应当把这种联动报成 REVIEW，而不是静默放行。

## 3. 数值（Balance）—— 本仓库实现

| 栏 | 内容 |
|---|---|
| 产出物 | 每个英雄／武器／技能的可调参数及其取值：伤害、射速、弹匣、装填、衰减起止距离、散布、冷却、生命／护甲／护盾 |
| 权威来源 | **取值以配置表（§5）为准**；设计意图以补丁意图说明为准；二者不一致时判 FAIL，不猜 |
| 上游 / 下游 | 读补丁意图；写 §5；被 §1 §2 §4 引用 |
| 机器可证 | 类型与单位正确；取值在字段定义的硬边界内；衰减随距离单调不增；联动字段同步修改（如改弹匣容量须同时给出装填时间处置）；改动方向与意图声明一致（意图写"削弱"而持续伤害上升 → FAIL） |
| 只能提示 | 同定位英雄之间持续伤害差、击杀所需时间（TTK）是否落在经验区间外；单次补丁对同一英雄叠加改动是否过量 |
| 留给人签字 | 这次改动是否达到设计目的；对高低分段的影响是否可接受 |
| Agent 可接 | **把自然语言补丁意图翻译成配置改动提案**，由校验器接受或拒绝；提案须逐条指回意图原句 |

## 4. 叙事与文案（Narrative）

| 栏 | 内容 |
|---|---|
| 产出物 | 英雄背景、技能描述文本、补丁说明对外文案、本地化文本 |
| 权威来源 | 文字以文案源文件为准；**文字里出现的数字以 §5 为准** |
| 上游 / 下游 | 读 §1 §3 §5；被客户端界面与对外公告引用 |
| 机器可证 | 技能描述与补丁文案中的每个数字能在配置表找到对应键且取值一致；各语言版本数字一致；无占位符残留 |
| 只能提示 | 描述用语与实际机制不符（写"短暂"而持续 6 秒）；同一机制在不同文本里叫法不一 |
| 留给人签字 | 语气、角色一致性、世界观 |
| Agent 可接 | 数值改动后列出所有需要同步修改的文案位置；起草补丁说明并过"文字数字 = 配置数字"检查 |

## 5. 配置表（Config Tables）—— 本仓库实现

| 栏 | 内容 |
|---|---|
| 产出物 | 结构化参数表（本仓库用 YAML／JSON）：字段定义（schema）＋取值＋每条取值的出处与抓取日期 |
| 权威来源 | **本表即全仓库数值的唯一权威**；基线只能用显式命令更新，普通运行只读 |
| 上游 / 下游 | 写入方只有"通过校验的改动提案"；被 §1–§4 全部读取 |
| 机器可证 | 符合 schema；主键唯一；引用完整（表间外键存在）；每条取值带来源与日期；改动以 diff 形式提交且 diff 可逆 |
| 只能提示 | 取值来源超过一个版本周期未复核 |
| 留给人签字 | 基线更新的批准 |
| Agent 可接 | 生成 diff、跑校验、对被拒的提案读取拒绝原因后重提（次数有上限，超限转人工） |

## 6. 资源管线（Assets）

| 栏 | 内容 |
|---|---|
| 产出物 | 模型、贴图、动画、音效、特效及其清单（manifest） |
| 权威来源 | 资产清单为准；配置表只存资产 ID，不存路径 |
| 上游 / 下游 | 被 §1（特效／音效触发）、§2（场景）、§5（ID 引用）读取 |
| 机器可证 | 命名规范；配置表引用的资产 ID 在清单中存在；无孤儿资产；体积与面数在预算内 |
| 只能提示 | 特效时长与技能持续时间差异过大；同类资产风格参数离群 |
| 留给人签字 | 美术品质、风格统一 |
| Agent 可接 | 引用完整性检查；预算超限报告；新技能所需资产清单草稿 |

## 7. 依赖关系

```text
补丁意图 ──► §3 数值 ──► §5 配置表 ──► §1 战斗（运行时读取）
                 │            │
                 │            ├──► §4 文案（数字一致性）
                 │            └──► §6 资源（ID 引用）
                 └──► §2 关卡（有效距离 × 视线长度）
```

一次平衡性补丁从左上角进入。本仓库实现的竖切是 `补丁意图 → §3 → §5`，并对 `§4`、`§2` 两条下游各保留一个联动检查的接口位（先报 REVIEW，不实现对端）。

## 8. 执行与审核的分工

| 角色 | 读什么 | 产出什么 | 不许做什么 |
|---|---|---|---|
| 执行 Agent | 补丁意图、字段定义、当前基线 | 配置改动提案（diff＋逐条指回意图原句） | 不许改基线；不许改校验器；不许自评通过 |
| 校验器 | 提案、字段定义、不变量 | 四态报告＋退出码 | 启发式命中不许判 FAIL；异常不许返回成功 |
| 审核 Agent | **只读改动后的配置 diff**，不读执行方的说明与校验报告 | 反推出的"这次补丁想干什么"，与原意图比对 | 不许读执行方总结（防自证） |
| 人 | 校验报告、REVIEW 处置记录、审核比对结果 | 签字或打回；REVIEW 决定逐条写入决定文件并带理由与限定范围 | 不许做全局豁免 |

终态只到 `READY_FOR_HUMAN_REVIEW`，不设自动批准。

## 9. 待向管线负责人确认的问题

外部拆解必然有猜错的地方。以下几项在真实管线里的答案会直接改变规范写法：

1. 数值的权威来源是表格工具、引擎内数据资产，还是代码常量？是否存在多处并存？
2. 配置改动走什么评审与合入流程？热更与随版本发布是否两套路径？
3. 5v5 与 6v6 等多模式下，同一参数是分表、分列还是覆盖层？（官方补丁说明里已出现同一参数按模式给不同取值。）
4. 文案里的数字是手写还是从配置表模板化生成？
5. 关卡度量（视线长度等）现在是否有导出工具？
